OVERVIEW
================================================================================

This report covers the build-out of an end-to-end SFT (supervised fine-tuning)
data generation pipeline on top of the existing skillmix-n-skillsbench stack.

The atomic SFT row we are producing:

    INPUT  : task passage + question, with a procedural Skill block injected
             into the system prompt.
    OUTPUT : the model's full chain-of-thought ending in an "ANSWER:" line.
    LABEL  : judge verdict (passed / score / conclusion_reached).

The training contract is "apply-given-skill": teach the student model to
follow a procedural skill block when one appears in its system prompt, and
to make its application of each procedure step visible in the response text.

End-to-end pipeline (procedural-skill SFT path):

    catalog        s2.m1 wikipedia_seeder       (declarative skills)
    bench_catalog  procedural_catalog rewrite   (procedure / constraints / example)
    s3.m5          extracted_task_synthesis     (NEW — skill -> ExtractedTask[N])
    bench_traced   s4.m4 --mode inject          (Gap A — solver + judge per condition)
    sft_dataset    sft_dataset.build_dataset    (NEW — filter -> JSONL chat format)

PIPELINE STAGES — WHAT EACH PRODUCES
================================================================================

Stage 1: catalog
  Input:   data/wikipedia-seed/source.json (10 named language skills)
  Output:  catalog/skills.json (declarative Skill records)
  Status:  PRE-EXISTING — unchanged this session.

Stage 2: bench_catalog
  Input:   catalog/skills.json
  Output:  bench_catalog/skills.json (procedural Skills)
  Procedure: Opus rewrites each declarative Skill into procedural form
             with When-to-use / numbered Procedure / Constraints / dual
             positive+negative Example.
  Status:  PRE-EXISTING — generated 2026-04-24 at $1.32 cost.

Stage 3: s3.m5 (NEW MODULE — added this session)
  File:    s3_generating_skill_examples/m5_extracted_task_synthesis.py
  Why it exists: closes the schema gap between s3.m1 (which produces
             SkillExample) and bench_traced (which consumes ExtractedTask).
             Without s3.m5, the only way to scale tasks was hand-writing.
  Input:   bench_catalog/skills.json + N (tasks per skill)
  Output:  synthesis/tasks.json + synthesis/task_skill_map.json sidecar
  Behavior: For each Skill, single Opus call returns N ExtractedTask records
             matching the bench_traced schema, tagged with skill_uid in
             acceptance_criteria. The prompt enforces:
               - skill must be necessary (no surface-readable answer)
               - include a TRAP for procedure-skipping models
               - exact-match-grade-able correct_conclusion
               - varied scenarios across the N tasks
               - one-shot schema anchor using t1 (modus-ponens)
  Status:  IMPLEMENTED + tested. Run on 2026-04-25 produced 100/100 valid
           tasks across 10 skills (0 malformed, 0 failures).

Stage 4: bench_traced (Gap A — added in earlier session)
  File:    s4_extracting_skill_usage_instances/m4_skill_composition_testing.py
  Mode:    --mode inject (the SFT-emission path)
  Per task: runs baseline (no skill in system) AND curated (procedural Skill
             injected via format_skill_as_system) episodes.
             Each episode: LinearAgent with thinking enabled, native CoT
             captured in response text, judge attached.
  Output:  bench_traced/episodes.jsonl (one record per (task, condition))
           bench_traced/summary.json (per-condition pass rates)
           Each record carries solution + trace + judge verdict.
  Status:  Currently RUNNING in background on the 100 synthesized tasks.
           Estimated ~2.5 hours walltime, ~$13 cost.

Stage 5: sft_dataset (NEW MODULE — added this session)
  File:    b2_benchmarks/skillsbench/sft_dataset.py
  Input:   bench_traced/episodes.jsonl
  Output:  sft_dataset/dataset.jsonl + sft_dataset/summary.json
  Filter (default v1):
             condition = curated
             judge_passed = True
             min_response_chars = 50  (drop one-line "ANSWER: yes" rows)
             dedup by (task_uid, condition, model)
  Format:  HuggingFace SFTTrainer / axolotl / unsloth chat schema.
             Each row: {messages: [system, user, assistant], metadata: {...}}
             system  = exact prompt sent during generation (incl. skill block)
             user    = exact user prompt sent (passage + question)
             assistant = full CoT response (reasoning + ANSWER: line)
             metadata = task_uid, skill_uid, skill_name, condition,
                        judge_score, judge_passed, judge_conclusion_reached,
                        judge_rationale, model_source, extraction_method
  Status:  IMPLEMENTED + tested on existing smoke episodes. Awaiting
           bench_traced output to run at scale.

PROMPT IMPROVEMENT (s4.m4 SOLVER_SYSTEM_PROMPT)

  - Before: "Think carefully... give your final answer as one concise
    conclusion." Opus interpreted "concise" as "be terse, skip thinking."
    Native thinking blocks were empty; response text was 11-13 tokens.
  - After: "Work through the task step by step in writing — explain your
    reasoning explicitly, then state your conclusion. If a SKILL block
    appears in the system prompt, follow its procedure explicitly: as
    you apply each step, name the step from the procedure you are
    applying. End your response with a line beginning exactly 'ANSWER: '..."
  - Result: 32x increase in trace richness. Curated responses now narrate
    each procedure step verbatim. Judge scores lifted from 0.40 -> 1.00
    on the test tasks.

PROCEDURAL_STEPS SPLITTER FIX

  - Before: only split native thinking_text into steps; if thinking was
    empty, fell back to a single 500-char chunk of the response.
  - After: if no native thinking, split the response text instead (after
    stripping the trailing ANSWER: line). Confirms 6+ procedural steps
    extracted from response-text CoT.

================================================================================
JUDGE BUG DISCOVERY + FIX
================================================================================

PROBLEM 1: deterministic-judge first-line extraction

  Pre-fix bench_traced reported baseline 21% / curated 19% — alarmingly low
  for Opus on Opus-designed tasks. Investigation showed the deterministic
  judge in b2_benchmarks/skillsbench/llm_judge.py was extracting the FIRST
  LINE of the response and comparing to expected. With the new step-by-step
  prompt, the first line is reasoning ('Step 1 (Scan for conditional): ...'),
  not the answer.

  Affected: 80% of synthesized tasks (52 YES_NO + 22 SINGLE_WORD + 6 RANKING).
  The 20 FREE_FORM tasks went through the LLM judge and were unaffected.

  FIX: Added _extract_answer_line() helper that:
    1. Looks for the last 'ANSWER:' line (the s4.m4 solver prompt format).
    2. Falls back to last 'Final answer:' / 'Conclusion:' / 'Verdict:' marker.
    3. Falls back to the last non-empty line, stripped of markdown formatting.

  Re-grading the existing bench_traced output flipped 124 of 200 verdicts.
  True baseline: 0.83 / curated: 0.81. Saved ~$13 by re-using existing
  episode data instead of re-running.

PROBLEM 2: markdown contamination on extracted answer

  Discovered when the multi-student bench run (corpus_harness, see next
  section) showed haiku at 30% baseline — implausibly low. Inspection of
  failures: judge rationales like "no match: expected 'yes', got 'yes**'"
  or "expected 'cooler', got '**'". corpus_harness uses a verbose-encouraging
  default reading-comprehension prompt; students wrote markdown-rich
  responses; my extractor returned '**yes**' or stray '**' tokens.

  This systematically PENALIZED larger models (which produce richer markdown).
  Effect was opposite of what student characterization needs.

  FIX: Extended _extract_answer_line() to:
    - Match marker patterns 'answer is X', 'conclusion: X', etc. (not just
      'ANSWER: X').
    - Aggressively strip leading/trailing markdown chars (* _ ` # > -)
      and trailing punctuation (. , ' ").

  Re-grading the existing bench-synthesis output flipped 124 of 800 verdicts
  (15.5%); haiku jumped from 30% baseline to 56% baseline; the relative
  ordering of students became coherent.

LEARNING

  Both bugs share a root cause: the deterministic judge was designed for
  TERSE answer-only responses (the original SkillsBench harness), not for
  step-by-step CoT or markdown-formatted reading-comprehension responses.
  Modern prompting styles broke its assumptions silently — verdicts looked
  like "model failed" rather than "judge couldn't find the answer."

  The fix landed in llm_judge.py and applies to ALL future bench/bench_traced
  runs automatically. Both bugs would have polluted SFT v1 if not caught.

MULTI-STUDENT BENCH RUN — STUDENT CHARACTERIZATION
================================================================================

PURPOSE

  Independent of the SFT corpus generation, characterize how 4 student
  models behave under skill injection on the SAME 100 synthesized tasks.
  This answers: "for which (student, skill) cells does the procedural
  skill help vs hurt?" — the prerequisite question for deciding which
  skills to prioritize in SFT v2.

COMMAND

  python3 -m b2_benchmarks.skillsbench.corpus_harness \
    --tasks          synthesis/tasks.json \
    --catalog        bench_catalog/skills.json \
    --task-skill-map synthesis/task_skill_map.json \
    --out-dir        bench-synthesis/ \
    --judge          anthropic:claude-opus-4-7 \
    --mode           singlecall \
    --models         "anthropic:claude-haiku-4-5-20251001,
                      ollama:llama3.1:8b,
                      ollama:qwen3.5:2b,
                      ollama:qwen3.5:0.8b"

SCOPE

  100 tasks x 4 students x 2 conditions = 800 episodes
  Cost: ~$30 (judge calls dominate; haiku ~$1, ollama free)
  Walltime: ~3 hours

PER-STUDENT AGGREGATE (post-rejudge)

      student                           BL pass   CU pass    Δ pass
      claude-haiku-4-5                    0.56      0.40     -0.16
      llama3.1:8b                         0.16      0.19     +0.03
      qwen3.5:0.8b                        0.20      0.28     +0.08
      qwen3.5:2b                          0.37      0.36     -0.01

CENTRAL FINDING — CAPABILITY INVERSION

  Skill injection helps WEAK models and distracts STRONG models. The
  strongest student (haiku) was hurt the most (-0.16); the weakest
  (qwen-0.8b) gained the most (+0.08). This is the dominant signal.

  The cleanest examples: red-herring and self-serving-bias. Both
  HURT haiku by -0.40 to -0.50, and both HELP qwen-0.8b by +0.20.
  Same skill, opposite effect, depending on capability.

PER-(SKILL, STUDENT) HEATMAP

  See data/pipeline-runs/default/bench-synthesis/heatmaps/per_skill_student.png
  for the 4-student x 10-skill matrix of:
        baseline pass rate
        curated pass rate
        delta pass rate (with green/red coloring)

  The auto-generated heatmaps in the same directory (uplift_heatmap.png,
  combined_heatmap.png, etc.) are at TASK granularity (100 rows) and
  hard to read for student characterization.

  Notable per-skill patterns:
    - red-herring:        haiku -0.40, qwen-0.8b +0.20 (large gradient)
    - self-serving-bias:  haiku -0.50, qwen-0.8b +0.20 (largest gradient)
    - modus-ponens:       qwen-0.8b +0.20, others flat
    - complex-question:   qwen-0.8b +0.30 (largest single lift)
    - metaphor:           Opus-only success; doesn't transfer to any student
    - spatial-reasoning:  universally weak (0.20-0.30 baseline); may indicate
                          task-quality issues, not student-skill issues

IMPLICATIONS FOR SFT V2

  Skills with a large lift gradient between weak and strong students are
  the highest-value SFT targets — the SFT corpus from Opus shows the
  procedure done right; the smaller student should learn to follow it.

  Best v2 targets: red-herring, self-serving-bias, modus-ponens, complex-question
  Worst v2 targets (for now): metaphor (no transfer), spatial-reasoning
                              (universal weakness; fix tasks first)
